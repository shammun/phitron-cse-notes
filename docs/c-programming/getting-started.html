    Getting started: compiler & first programs

    Before writing any real C, you need a working toolchain: a C compiler (GCC from MinGW on Windows), an editor (VS Code) and a quick way to run a file (the Code Runner extension). This page sums up that setup and the two tiny programs used to check that everything works: one that only prints, and one that reads a number.

    🧭 Start here

    If you have never compiled anything before, the first hour of C is confusing for a reason that has little to do with C. You write something, press a button, and three separate things happen at once. It is much easier once you pull them apart.

    What you write is plain text, nothing more. A file called test.c is the same kind of file as a shopping list; you could open it in Notepad. The line printf("Hello World!\n"); is a sentence in a language that you and one particular program both understand. The processor inside your computer does not understand it. It follows only a far simpler set of instructions, written as numbers.

    A compiler is the translator standing between the two. You hand it your text file, it reads the whole thing from top to bottom, and if every line makes sense it writes out a second file holding the same instructions in the form the machine can follow. On Windows that second file ends in .exe. The compiler used here is called gcc.

      test.c         gcc          test.exe        run
 ----------  ----------->  -------------  ---------->
 your text    translated     the machine    output on
             once           can read it    the screen

    So there are always two steps, never one. First translate, then run:

    gcc test.c -o test.exe
./test.exe

    In the first line, test.c is your text and -o test.exe names the file to write. In the second line gcc plays no part at all: test.exe is now an ordinary file sitting in the same folder, and you could run it again next week without compiling anything.

    Two things follow from this, and both catch beginners. If the compiler meets a line it cannot make sense of, it prints an error and writes no .exe at all. And if you change the .c file but forget to translate it again, running the old .exe runs yesterday's version, so it looks as though your edit did nothing. A Run button in an editor is simply something that does both steps for you in one click.

    The second thing to picture is how a running program talks to you. It has one stream of text going out to the screen and one coming in from your keyboard. printf is the outgoing one: whatever you give it appears in the terminal. scanf is the incoming one: the program stops, waits until you type something and press Enter, and stores what you typed in a variable you have set aside for it. The & in scanf("%d", &a) is how you say which variable to fill.

    Here is the whole of the second program on this page, test2.c. It is four useful lines:

    #include <stdio.h>

int main() {
    int a;
    scanf("%d", &a);
    printf("a = %d", a);
    return 0;
}
    step                      screen      a
1 you run test.exe        (nothing)   ?
2 scanf waits for you     (nothing)   ?
3 you type 42 and Enter   42          42
4 printf runs             a = 42      42

    Line 2 of the trace is the part that surprises people. The window sits there with nothing on it, and it looks as though the program has crashed. It has not; it is waiting. A program that seems frozen right at the start is nearly always stopped at a scanf, wanting you to type.

    That is also why there are two tiny programs on this page instead of one. The first only prints. If Hello World! appears, translating and running both worked, and that is the whole toolchain proved in a single line. The second adds input, which can fail on its own account: some editors show a program's output in a panel that can only display text and cannot take your typing, so scanf waits for a key that never arrives.

    The notes below cover the setup in order, then go through those two programs line by line. Get the printing one working first, and only then worry about input.

    💡 Key ideas

    Compiler

    C source code is plain text. A compiler (here gcc) turns it into an .exe the computer can run. You compile first, then run.

    gcc test.c -o test.exe
./test.exe

    PATH environment variable

    Windows only finds gcc from any folder if the compiler's bin folder is added to the Path system variable. Check it by opening a terminal and typing gcc -v; a version message means it worked.

    VS Code + Code Runner

    Code Runner adds a Run button that saves the file, compiles it and runs it in one click. Its executorMap setting (in settings.json) holds the exact compile-and-run command for each language.

    Run in the terminal

    Set code-runner.runInTerminal to true. The Output panel is read-only, so a program that calls scanf can only receive your typing inside the terminal.

    Online compiler as a backup

    If your local setup is broken, an online compiler such as OnlineGDB lets you keep practising while you fix it.

    First two sanity checks

    A print-only program proves that compiling and running work. A program that reads input proves that typing into the terminal works too.

    /*
 * Hello World - the very first program of the course.
 *
 * It does exactly one thing: print a line of text. That is the point. If
 * this runs, then the compiler, the editor and the Run button are all
 * working, and from here on you can blame your own code instead of the
 * setup.
 *
 * Running it is always two steps, never one:
 *     gcc test.c -o test.exe     translate this text into a program
 *     ./test.exe                 run that program
 * A Run button simply does both for you in one click.
 */

/* printf is not part of the C language itself; printing lives in a
 * library. This line pastes in <stdio.h> ("standard input output"),
 * which tells the compiler that printf exists and how it is called.
 * Leave it out and the compiler does not recognise the name at all. */
#include <stdio.h>

/* Execution starts here. Every C program has exactly one function called
 * main, and the curly braces hold the steps it runs, in order, from top
 * to bottom. The int in front says main hands a whole number back when
 * it finishes. */
int main() {
    /* Send the text to the screen. \n is not two characters: inside a
     * string it means one "newline", which moves the cursor to the start
     * of the next line. Leave it out and whatever prints next sticks
     * straight onto Hello World!. */
    printf("Hello World!\n");

    /* Hand 0 back to the operating system: "I finished, nothing went
     * wrong". Any other number would be a way of reporting a failure. */
    return 0;
}
    Input

    This program reads no input.

    Output 
    Hello World!

    Reading the output. You should see exactly Hello World! on one line.

    How it works, step by step
    1. #include <stdio.h> brings in printf.
    2. main is where the program starts running.
    3. printf("Hello World!\n") prints the text; \n moves to a new line.
    4. return 0; tells the operating system the program finished without errors.
    Watch out. If the terminal says gcc is not recognized, the MinGW bin folder is not in your Path yet.
    ✅ Check yourself: What does return 0; at the end of main mean?
    The program finished successfully. A non-zero value would signal an error.

    /*
 * Read one number and print it back.
 *
 * Hello World proved that the program can talk to you. This one proves
 * that you can talk to the program. That is a separate thing and it can
 * fail on its own: some editors show a program's output in a panel that
 * can only display text and cannot accept typing, so the program waits
 * for a key that never arrives and looks as though it has frozen.
 *
 * A program that seems stuck right at the start is nearly always sitting
 * at a scanf, waiting for you.
 */

#include<stdio.h>   /* printf and scanf both come from this header */

int main() {
    /* Ask for a box big enough to hold one whole number and call it a.
     * Nothing has been put in it yet, so at this moment it holds
     * whatever rubbish was in that memory before. */
    int a;

    /* Stop here until you type something and press Enter.
     *   "%d"  says what to expect: one whole number written in digits.
     *   &a    means "the address of the box a". scanf has to put a value
     *         INTO that box, so it must be told where the box is.
     * The missing & is the classic first-week mistake. */
    scanf("%d", &a);

    /* Print it again. Here a is written without &, because printf only
     * reads the value; it never changes the variable, so it does not
     * need the address.
     * There is no \n at the end, so when the program stops your terminal
     * prompt appears on the same line as the answer. */
    printf("a = %d", a);

    return 0;   /* finished successfully */
}
    Input (stdin)
    42

    One integer.

    Output 
    a = 42

    Reading the output. With input 42 the program prints a = 42. There is no \n at the end, so your terminal prompt may appear on the same line.

    How it works, step by step
    1. Declare int a; to hold the number.
    2. scanf("%d", &a) waits for you to type an integer. &a gives scanf the address where it should store the value.
    3. printf("a = %d", a) replaces %d with the value of a.
    Watch out. If the program seems stuck, it is waiting for input. Type a number and press Enter. With Code Runner this only works when runInTerminal is on.
    ✅ Check yourself: Why do we write &a in scanf but just a in printf?
    scanf must change a, so it needs the variable's address. printf only needs its value.

    📌 Remember

    • The workflow is always the same: write, compile with gcc, then run the .exe.
    • Add MinGW's bin folder to Path, then check with gcc -v.
    • In VS Code, Code Runner plus runInTerminal: true lets you run programs that read input.
    • printf writes output and scanf reads input. Both come from <stdio.h>.
    • Get Hello World running first, then test input.

    ✅ Check yourself

    You typed gcc -v and got 'command not found'. What is the most likely cause?
    The compiler's bin folder is not in the Path environment variable, or you did not open a new terminal after adding it.
    Why can't a program that uses scanf read your typing in VS Code's Output panel?
    The Output panel only shows text; it cannot send keyboard input. Run the program in the integrated terminal instead.
    What two steps happen when you press Run on a .c file?
    The file is compiled into an executable, and then that executable is run.
